# 지식 저장 구조 결정: 도메인, 세부 주제, MOC

- 날짜: 2026-09-29
- 상태: 방향 합의. 구현 계획과 구현은 별도.
- 목적: 이후 Synesis 계획에서 이번 대화의 결정을 다시 추측하지 않고 참조한다.
- 적용 범위: 지식의 디렉터리 구조, 목차의 역할, 사용자와 모델의 책임 분담.

## 배경

사용자는 AI, 육아, 개발처럼 서로 다른 관심 영역의 지식을 쌓고 싶다.
기본 디렉터리 구조는 직접 정하되, 개별 자료의 배치와 목차 관리는 모델에게 맡긴다.

기대하는 사용 흐름은 다음과 같다.

```text
링크 또는 직접 입력한 생각
  -> 커맨드나 스킬 활성화
  -> 개인 인사이트를 도출하는 몇 차례의 질문과 답변
  -> 원본 내용 또는 요약과 개인 인사이트 저장
  -> 나중에 관련 지식 조회
```

질문의 정확한 횟수와 저장 승인 절차는 이번 대화에서 정하지 않았다.

## 결정

### D1. 역할보다 도메인을 먼저 나눈다

최상위 지식 영역은 사용자가 정한 도메인이다. 그 아래에 세부 주제를 둘 수 있다.
원본과 개인 인사이트는 해당 주제 안에서 구분한다.

```text
도메인 -> 세부 주제 -> 원본 / 개인 인사이트
```

`AI`, `육아`, `개발`은 사용자가 제시한 관심 영역이다.
모든 사용자에게 이 세 폴더를 강제하는 기본값이라는 뜻은 아니다.
KM의 `Mine/Library` 구분을 최상위 구조로 채택한 것도 아니다.

### D2. 기본 구조는 사용자가, 배치와 목차는 모델이 관리한다

| 사용자 | 모델 |
|---|---|
| 최상위 도메인과 기본 구조 결정 | 기존 도메인과 세부 주제 중 저장 위치 판단 |
| 기본 구조를 바꿀지 결정 | MOC 생성 및 갱신 |

모델이 최상위 구조를 임의로 바꾸는 방식은 채택하지 않는다.
세부 주제 신설, 이동, 병합을 어느 범위까지 자동으로 할지는 계획에서 구체화한다.

### D3. 영역과 주제의 대표 Markdown 문서는 MOC다

MOC(Map of Content)는 관련 지식으로 들어가는 목차이자 허브 노트다.
폴더가 보관 위치라면 MOC는 그 지식을 이해하고 찾아가는 안내 문서다.

아래 경로는 역할을 설명하는 예시이며, 정확한 파일명과 루트 진입점 형식은 계획에서 정한다.

| 예시 문서 | 역할 |
|---|---|
| 루트 `index.md` | vault 전체의 진입점 |
| `AI/AI.md`, `육아/육아.md` 등 | 도메인 MOC |
| `육아/수면/수면.md` 등 | 세부 주제 MOC |
| `sources/` 안의 노트 | 원본 내용 또는 요약과 출처 |
| `insights/` 안의 노트 | 대화에서 도출한 개인 인사이트 |

`육아.md`라는 이름으로도 MOC 역할을 할 수 있다.
파일명에 `-MOC`를 반드시 붙일 필요는 없다.
MOC는 단순 파일 목록뿐 아니라 연결 이유, 읽는 순서, 남은 질문도 담을 수 있다.
이 내용의 정리와 갱신은 모델에게 맡긴다.

## 합의한 방향을 나타내는 예시

아래 트리는 구조의 예시다. 세부 주제 이름과 빈 폴더 전체를 미리 생성하라는 요구는 아니다.
파일명 규칙과 필수 메타데이터 스키마도 아직 확정하지 않았다.

```text
Vault/
├── index.md
├── AI/
│   ├── AI.md
│   ├── 에이전트/
│   │   ├── 에이전트.md
│   │   ├── sources/
│   │   │   └── AI 위임에 관한 글.md
│   │   └── insights/
│   │       └── 검증 가능한 작업부터 위임한다.md
│   └── 모델 평가/
│       ├── 모델 평가.md
│       ├── sources/
│       └── insights/
├── 육아/
│   ├── 육아.md
│   ├── 수면/
│   │   ├── 수면.md
│   │   ├── sources/
│   │   └── insights/
│   └── 의사소통/
│       ├── 의사소통.md
│       ├── sources/
│       └── insights/
└── 개발/
    ├── 개발.md
    ├── 아키텍처/
    │   ├── 아키텍처.md
    │   ├── sources/
    │   └── insights/
    └── 테스트/
        ├── 테스트.md
        ├── sources/
        └── insights/
```

탐색 예시:

```text
index.md -> 육아.md -> 수면.md -> 관련 원본과 개인 인사이트
```

## 후속 계획에서 검토할 제안

다음은 이번 대화에서 제안한 운영 기준으로, D1-D3과 구분한다.
개별 정책까지 확정한 것은 아니며, 채택 여부와 구체적인 수락 조건은 다음 계획에서 정한다.

- 기본적인 의미 분류는 `도메인 -> 세부 주제`로 시작한다.
  `sources/insights`는 주제 분류가 아니라 기록 역할의 구분이다.
- 처음부터 모든 영역을 같은 깊이로 채우지 않는다.
  더 세밀한 구분은 우선 MOC 안의 절로 표현하고, 필요할 때 폴더 분리를 검토한다.
- 여러 영역에 걸친 기록은 주 저장 위치 하나를 두고 다른 MOC에서 연결한다.
  같은 내용을 영역마다 복사하는 방식은 기본으로 삼지 않는다.
- 저장 전에 관련 기존 노트와 MOC를 확인한다.
  신규 노트를 만들었으면 관련 MOC와의 연결도 함께 관리한다.
- 검색은 관련 MOC에서 시작할 수 있지만, 해당 폴더에 없다는 이유만으로
  vault 전체에 관련 지식이 없다고 단정하지 않는다.
- 원문의 주장과 사용자의 해석을 구별한다.
  외부 출처가 없는 직접 입력도 개인 인사이트로 저장할 수 있어야 한다.

## 아직 정하지 않은 것

- 최상위 도메인의 초기 목록, 숫자 접두사와 구체적인 파일명 규칙.
- 세부 주제가 아직 없는 도메인의 저장 위치와 하위 폴더 생성 시점.
- 세부 주제 신설, 추가 깊이, 이동, 병합에 대한 자동화 범위와 승인 방식.
- 한 입력에서 원본과 인사이트를 몇 개의 노트로 나눌지, 대화 기록을 얼마나 보존할지.
- MOC의 필수 절, frontmatter, 자동 생성 영역과 사용자 작성 영역의 경계.
- 동명 노트의 식별과 링크 형식, 출처 중복 및 원문 버전 처리.
- 과거 인사이트와 현재 이해를 어떻게 구분하고 갱신할지.
  별도 `wiki/` 계층의 필요 여부와 위치는 이번 결정에서 확정하지 않았다.
- 검색 엔진, CLI, 별도 큐레이터 에이전트, 기존 vault 이전 방식.

## 이전 설계와의 관계

로컬에 남아 있는 이전 문서:

- `.omc/specs/deep-interview-synesis-vault-structure.md`, Addendum E
- `.omc/plans/synesis-minimal.md`

이전 최소 설계는 도메인 바로 아래 `wiki/`, `sources/`, `insights/`를 두고
세부 분류를 보류했다. 이번 결정은 **도메인 아래 세부 주제와 그 MOC를 두는 방향**을
채택하므로, 이후 구조 계획에서는 그 차이를 반영해야 한다.

구조와 MOC에 관해 충돌하는 부분은 이 결정 기록을 기준으로 계획을 갱신한다.
이 문서가 이전 계획 전체를 승인하거나 폐기하는 것은 아니다.
CLI, 에이전트 구성, 마이그레이션 등 나머지 항목은 이번 대화에서 재확정하지 않았다.

`.omc/`는 현재 Git 추적 대상이 아니므로, 이번 결정은 저장소에 보관할 수 있는
`docs/decisions/`에 남긴다.

계획을 시작할 때 이 문서를 읽고 D1-D3을 구조 요구사항으로 인용한다.
예시 트리의 세부 주제나 미결정 항목을 이미 승인된 구현 요구사항으로 취급하지 않는다.

계획 요청 예시:

> 도메인/세부 주제 계층과 MOC 역할, 사용자와 모델의 책임 분담을 반영하고,
> 아직 정하지 않은 항목은 구현 전에 결정할 수 있도록 분리해줘.
